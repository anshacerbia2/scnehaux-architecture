# ADR-IAM-002: Token Signing Algorithm and Key Lifecycle Management

## 1. Title

Token Signing Algorithm and Key Lifecycle Management.

## 2. Status

| Date       | Status   | ADR Type     | Reviewers                 | Approver             |
| ---------- | -------- | ------------ | ------------------------- | -------------------- |
| 2026-08-18 | accepted | foundational | Architecture Review Board | Enterprise Architect |

## 3. Context

The Scnehaux Identity Runtime issues signed JSON Web Tokens, and every protected resource verifies them locally, on every hop, without calling Identity (`STD-IAM-002`). Two choices decide how safe that is: the algorithm tokens are signed with, and how a signing key comes into use, stays trusted, and leaves.

The identity kernel holds the signing keys and publishes their public halves as the realm's JWKS (`ADR-IAM-001`). It signs with a key pair it holds: its RSA key providers generate a pair, import one, or load one from a keystore [R11]. A key it still publishes to verify earlier tokens is a passive key, which verifies and no longer signs [R11].

The ecosystem pulls in two directions:

- RFC 9068 requires authorization and resource servers to support `RS256` [R4], and OpenID Connect Core requires an OpenID Provider to support it for ID tokens [R5].
- The FAPI 2.0 Security Profile, the OpenID Foundation's security profile for high-value APIs, permits `PS256`, `ES256` and `Ed25519` and not `RS256` [R9].

## 4. Decision Drivers

- **One verification path.** Algorithm confusion, where a verifier lets the token's header choose the algorithm, is a known and exploited defect class [R3]. Every algorithm a verifier accepts is a branch where it can live.
- **A signature scheme with a security proof.** RSASSA-PSS has one and PKCS#1 v1.5 does not, and RFC 8017 requires PSS in new applications [R2].
- **Trust continuity.** A rotation must never fail a valid token, and a compromise must stop trust in the compromised key at once.
- **Custody.** Key material must be identical on every replica and never generated by one (`STD-IAM-001 §3.5`), and a private signing key must not outlive its use [R6].
- **Cost on the path that repeats.** A token is signed once and verified on every hop.

## 5. Decision

### 5.1 Signing Algorithm: a Single `PS256` Baseline

1. **Every audience class**: tokens are signed with **`PS256`** (RSASSA-PSS with SHA-256) [R1], with an RSA modulus of at least **3072 bits**, which gives 128-bit security strength [R6].
2. **Single-algorithm JWKS**: the enterprise JWKS advertises `PS256` keys only.
3. **`RS256` by exception**: permitted for an `external` registration whose relying party cannot verify `PS256`, and only with a named accountable owner, a recorded reason, and an expiry date. `ES256` and `Ed25519` are not adopted.

The operative profile is `STD-IAM-002 §3.2.2`, which fixes the allowlist and the exception form. `none` and every symmetric algorithm are prohibited, and a verifier determines the expected algorithm from its own configuration, never from the token [R3].

**This departs from two mandatory-to-implement rules on purpose.** RFC 9068 §2.1 and OpenID Connect Core §15.1 require `RS256` support [R4][R5]. The baseline follows FAPI 2.0 instead [R9], as FAPI 1.0 did when it said `RS256` should not be used [R10]. `RS256` is PKCS#1 v1.5, which carries no security proof [R2], and supporting it beside `PS256` puts back the second verification path the baseline exists to remove. A relying party that can verify only `RS256` is served through the exception, and no internal resource accepts it.

**The cost is measured, and small.** A `PS256` signature over a 3072-bit key is 384 bytes, and an `ES256` signature is 64 [R1]. Encoded, that is 426 characters more per token, well inside any header budget. Verification runs the other way: on one core, OpenSSL 3.5 verified RSA-3072 signatures about 1.7 times faster than ECDSA P-256 signatures, and signed them about 37 times slower [R13]. The token is signed once and verified on every hop, so the operation this estate repeats is the one `PS256` does faster. No standard states these figures; they are a measurement, and they support "not slower", not more.

### 5.2 Key Lifecycle, Aligned with NIST SP 800-57

A signing key passes through the states below. Each maps to a state NIST SP 800-57 defines [R6], and identity-kernel's signing key custody design realizes them.

| State      | NIST SP 800-57 state | Signs | In JWKS | Private material |
| :--------- | :------------------- | :---- | :------ | :--------------- |
| `staged`   | Pre-activation       | No    | Yes     | In custody       |
| `active`   | Active               | Yes   | Yes     | In custody       |
| `retiring` | Deactivated          | No    | Yes     | In custody       |
| `retired`  | Destroyed            | No    | No      | Destroyed        |
| `revoked`  | Compromised          | No    | No      | Destroyed        |

- **A key is published before it signs.** It stays `staged` until every consumer's JWKS cache can hold it, so a consumer never meets a `kid` it cannot resolve during a routine rotation. A consumer that does refetches the JWKS, rate-limited [R5].
- **Exactly one key is `active`.** Two would make which key signed a token a matter of chance.
- **A `retiring` key verifies and no longer signs**, as the kernel's passive key does [R11]. It stays published for the longest access token lifetime plus the consumer JWKS cache plus the clock-skew allowance (`STD-IAM-001 §3.5`). Refresh tokens do not enter the window: the kernel signs them with an internal HMAC key, not a realm signing key [R12].
- **The private material is destroyed when the key leaves the JWKS, and is never archived** [R6]. A private signature key has no use after its signing period, and a copy kept in cold storage is a copy that can still sign. The kernel publishes a key only from the key pair it holds [R11], so the private material stays in custody while the key is `retiring` and no longer. The public key and the key's record are kept as evidence, which SP 800-57 permits [R6].
- **A compromised key is `revoked` at once.** It leaves the JWKS without a retirement window, a replacement is activated, and every token it signed fails verification from that moment. That failure is the containment.
- **A `kid` is the RFC 7638 thumbprint of its public key** [R7], so different material cannot carry the same identifier (`STD-IAM-001 §3.5`).

### 5.3 Key Custody

- **Shared environments.** A signing key is generated once, under a ceremony, sealed in the approved secret manager, and delivered identically to every replica as a keystore the kernel loads [R11]. No replica generates key material, and a replica that cannot reach custody refuses to start (`STD-IAM-001 §3.5`).
- **Non-exportable custody is a later phase.** A KMS or HSM that never releases the private key is adopted when an audit or regulatory obligation requires it. The pinned kernel's key providers hold the key pair themselves [R11], so that phase needs a kernel integration the pinned release does not document, and it is decided in its own ADR.
- **A throwaway kernel**, such as a test run's, may sign with a key it generated itself, because nothing outside that run verifies its tokens.

## 6. Consequences

### Positive

- One algorithm, one key lifecycle, and no algorithm branch in any verifier.
- A rotation fails no valid token, and a compromise ends trust in a key at once.
- No private signing key outlives its use, and none exists outside approved custody.

### Negative

- A relying party that can verify only `RS256` needs an exception record, with an owner and an expiry.
- The platform declares a departure from RFC 9068 §2.1 and OpenID Connect Core §15.1, which a conformance test would report.
- Tokens are about 426 bytes larger than `ES256` tokens.
- A key ceremony is an operation two people must be available for.

### Operational

- The rotation schedule publishes the next key before activating it, and the retirement window is recomputed from the live token lifetime classes rather than read as a constant.
- The identity kernel's compatibility suite proves `PS256` issuance and verification on every candidate release; a candidate that cannot issue `PS256` is not promoted.
- The secret manager holds the only copy of an active or retiring private key; destroying it at retirement is part of the rotation, and is recorded.

## 8. Alternatives Considered

### Alternative A: `ES256` Only

- **Pros**: the most compact tokens, and an algorithm FAPI 2.0 permits [R9].
- **Cons**: ECDSA verification is the slower operation on the path that repeats [R13]. An `ES256` signature is the raw concatenation of R and S [R1], while signing services such as Vault Transit produce ASN.1 DER by default [R14], so every signer needs a conversion that is a known source of defects.
- **Why Rejected**: it saves header bytes and pays for them on every verification.

### Alternative B: Ephemeral Keys in Production

- **Pros**: no custody to operate.
- **Cons**: a key generated by one replica is unknown to the others, so tokens it signs fail verification elsewhere, and every restart replaces the key and fails every token signed before it.
- **Why Rejected**: it breaks verification continuity, which `STD-IAM-001 §3.5` exists to guarantee.

### Alternative C: `ES256` Internally and `RS256` Externally

- **Pros**: the compact-token argument for internal traffic, and `RS256` acceptance by every relying party without an exception record.
- **Cons**: two algorithms require two key lifecycles and an algorithm branch in every verifier, which is where algorithm confusion lives [R3]. The external half selects PKCS#1 v1.5, which carries no security proof [R2] and which FAPI rejects [R9][R10].
- **Why Rejected**: it pays in key custody and verifier surface for a saving too small to matter.

### Alternative D: `Ed25519` as the Baseline

- **Pros**: compact, fast, and deterministic, so free of the nonce-reuse failure that makes ECDSA implementations fragile [R8]; FAPI 2.0 permits it [R9].
- **Cons**: in this platform's assessment, relying-party and gateway support across the OpenID Connect ecosystem is thinner than for RSA, and an external party that cannot verify it has no fallback inside a single-algorithm profile.
- **Why Rejected**: the stronger choice cryptographically and the riskier one for a profile that must also serve external federation. Revisit when relying-party support is no longer the limit.

### Alternative E: Support `RS256` Beside `PS256`, to Conform to RFC 9068

- **Pros**: conformance with the mandatory-to-implement rules of RFC 9068 and OpenID Connect Core [R4][R5], and no exception records.
- **Cons**: it is Alternative C's second key lifecycle and verifier branch again, for an algorithm without a security proof.
- **Why Rejected**: the exception serves the relying parties that need `RS256`, and nothing else in the estate does.
