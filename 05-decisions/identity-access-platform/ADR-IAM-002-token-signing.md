## 3. Context

The Scnehaux Identity Runtime issues signed JSON Web Tokens, and every protected resource verifies them locally, on every hop, without calling Identity (`STD-IAM-002`). Two choices decide how safe that is: the algorithm tokens are signed with, and how a signing key comes into use, stays trusted, and leaves.

The identity kernel holds the signing keys and publishes their public halves as the realm's JWKS (`ADR-IAM-001`). It signs with a key pair it holds: its RSA key providers generate a pair, import one, or load one from a keystore [R11]. A key it still publishes to verify earlier tokens is a passive key, which verifies and no longer signs [R11].

The ecosystem pulls in two directions:

- RFC 9068 requires authorization and resource servers to support `RS256` [R4], and OpenID Connect Core requires an OpenID Provider to support it for ID tokens [R5].
- The FAPI 2.0 Security Profile, the OpenID Foundation's security profile for high-value APIs, permits `PS256`, `ES256` and `Ed25519` and not `RS256` [R9].

## 4. Decision Drivers

- **One verification path.** Algorithm confusion, where a verifier lets the token's header choose the algorithm, is a known and exploited defect class [R3]. Every algorithm a verifier accepts is a branch where it can live.
- **A signature scheme with a security proof.** RSASSA-PSS has one and PKCS#1 v1.5 does not, and RFC 8017 requires PSS in new applications [R2].
- **Trust continuity.** A rotation must never fail a valid token, and a compromise must stop trust in the compromised key at once.
- **Custody.** Key material must be identical on every replica and never generated by one (`STD-IAM-001 §3.5`), and a private signing key must not outlive its use [R6].
- **Cost on the path that repeats.** A token is signed once and verified on every hop.

## 5. Decision

### 5.1 Signing Algorithm: a Single `PS256` Baseline

1. **Every audience class**: tokens are signed with **`PS256`** (RSASSA-PSS with SHA-256) [R1], with an RSA modulus of at least **3072 bits**, which gives 128-bit security strength [R6].
2. **Single-algorithm JWKS**: the enterprise JWKS advertises `PS256` keys only.
3. **`RS256` by exception**: permitted for an `external` registration whose relying party cannot verify `PS256`, and only with a named accountable owner, a recorded reason, and an expiry date. `ES256` and `Ed25519` are not adopted.

The operative profile is `STD-IAM-002 §3.2.2`, which fixes the allowlist and the exception form. `none` and every symmetric algorithm are prohibited, and a verifier determines the expected algorithm from its own configuration, never from the token [R3].

**This departs from two mandatory-to-implement rules on purpose.** RFC 9068 §2.1 and OpenID Connect Core §15.1 require `RS256` support [R4][R5]. The baseline follows FAPI 2.0 instead [R9], as FAPI 1.0 did when it said `RS256` should not be used [R10]. `RS256` is PKCS#1 v1.5, which carries no security proof [R2], and supporting it beside `PS256` puts back the second verification path the baseline exists to remove. A relying party that can verify only `RS256` is served through the exception, and no internal resource accepts it.

**The cost is measured, and small.** A `PS256` signature over a 3072-bit key is 384 bytes, and an `ES256` signature is 64 [R1]. Encoded, that is 426 characters more per token, well inside any header budget. Verification runs the other way: on one core, OpenSSL 3.5 verified RSA-3072 signatures about 1.7 times faster than ECDSA P-256 signatures, and signed them about 37 times slower [R13]. The token is signed once and verified on every hop, so the operation this estate repeats is the one `PS256` does faster. No standard states these figures; they are a measurement, and they support "not slower", not more.

### 5.2 Key Lifecycle, Aligned with NIST SP 800-57

A signing key passes through the states below. Each maps to a state NIST SP 800-57 defines [R6], and identity-kernel's signing key custody design realizes them.

| State      | NIST SP 800-57 state | Signs | In JWKS | Private material |
| :--------- | :------------------- | :---- | :------ | :--------------- |
| `staged`   | Pre-activation       | No    | Yes     | In custody       |
| `active`   | Active               | Yes   | Yes     | In custody       |
| `retiring` | Deactivated          | No    | Yes     | In custody       |
| `retired`  | Destroyed            | No    | No      | Destroyed        |
| `revoked`  | Compromised          | No    | No      | Destroyed        |

- **A key is published before it signs.** It stays `staged` until every consumer's JWKS cache can hold it, so a consumer never meets a `kid` it cannot resolve during a routine rotation. A consumer that does refetches the JWKS, rate-limited [R5].
- **Exactly one key is `active`.** Two would make which key signed a token a matter of chance.
- **A `retiring` key verifies and no longer signs**, as the kernel's passive key does [R11]. It stays published for the longest access token lifetime plus the consumer JWKS cache plus the clock-skew allowance (`STD-IAM-001 §3.5`). Refresh tokens do not enter the window: the kernel signs them with an internal HMAC key, not a realm signing key [R12].
- **The private material is destroyed when the key leaves the JWKS, and is never archived** [R6]. A private signature key has no use after its signing period, and a copy kept in cold storage is a copy that can still sign. The kernel publishes a key only from the key pair it holds [R11], so the private material stays in custody while the key is `retiring` and no longer. The public key and the key's record are kept as evidence, which SP 800-57 permits [R6].
- **A compromised key is `revoked` at once.** It leaves the JWKS without a retirement window, a replacement is activated, and every token it signed fails verification once a consumer's key set refreshes, which is at most the consumer JWKS cache lifetime later (amended 2026-10-24, §5.5 Q7). That failure is the containment.
- **A `kid` is the RFC 7638 thumbprint of its public key** [R7], so different material cannot carry the same identifier (`STD-IAM-001 §3.5`).

### 5.3 Key Custody

- **Shared environments.** A signing key is generated once, under a ceremony, sealed in the approved secret manager, and delivered identically to every replica as a keystore the kernel loads [R11]. No replica generates key material, and a replica that cannot reach custody refuses to start (`STD-IAM-001 §3.5`). The ceremony follows `STD-IAM-001 §3.10`: two people, recorded, and an independent review.
- **The secret manager is AWS Secrets Manager, under a customer-managed AWS KMS key (amended 2026-10-20).** AWS is the adopted cloud (`tech-radar.yaml`), and `EAD-005` asks for "Managed KMS/HSM and secret management". The secret holds the sealed keystore, PKCS#12 or BCFKS. A keystore with one RSA-3072 pair fits in a secret value of at most "65,536 Bytes" [R19].
  - Secrets Manager "uses envelope encryption with AWS KMS keys and data keys to protect each secret value" [R16]. KMS keys "are protected by FIPS 140-3 Security Level 3 validated hardware security modules (HSM). They never leave AWS KMS unencrypted" [R15].
  - **A customer-managed key, not the AWS-managed `aws/secretsmanager` key.** AWS: "To be able to access a secret from another account or to apply a key policy to the encryption key, use a customer managed key to encrypt the secret" [R17]. The key policy lets only the kernel pods' role decrypt, and keeps the key's administrators apart from its readers, the separation of duties NIST AC-5 asks for (`STD-IAM-001 §3.10`). `EAD-006 §6.9` already asks that secrets use managed custody. AWS also asks for "the principle of least privileged access" in every policy on the secret [R17].
  - **One KMS key per environment and realm, and two secrets per signing key: its keystore and its password (amended 2026-10-24, §5.5 Q3, Q8).** No environment shares key material with another, by construction, and no key shares a secret with another.
  - **Every read is recorded.** "AWS CloudTrail records all API calls for Secrets Manager as events" [R21]. That is the native source of the privileged-access event on every custody access.
- **Delivery is a file the kernel loads.** The AWS Secrets and Configuration Provider (ASCP) mounts the secret into each kernel pod as a file: "To determine which secrets the ASCP mounts in Amazon EKS as files on the filesystem, you create a SecretProviderClass YAML file" [R20]. The kernel's `java-keystore` provider loads it: "To add a key pair and certificate stored in a Java Keystore file on the host select Providers and choose java-keystore from the dropdown", with "Keystore Type (JKS, PKCS12 or BCFKS)" [R11].
  - **Both passwords are vault references,** `${vault.…}`, never literal realm configuration. The keystore password and the key password each "can refer a value from an external vault" [R11]. The kernel's file vault reads them from a mounted directory: "You can mount Kubernetes secrets into the Keycloak Container, and the data fields will be available in the mounted folder with a flat-file structure" [R18].
- **Development server.** The keystore is a file in identity-kernel's `deploy/dev/keys/`, mode 0400, owned by the container's user, with its passwords in the file vault directory. Both are mounted read-only, and the kernel refuses to start when either is missing.
  - **It is never copied to backup storage.** NIST SP 800-57 gives the backup of a private signature key as "No (in general); support for non-repudiation would be in question" [R6]. The development server is redeployed from zero, so a lost development keystore is replaced by a new ceremony and a new `kid`, never restored (`STD-GLB-009` rule 9).
  - Its protection on a single host is access control and sealing. NIST permits keys "stored externally (provided that proper protection is afforded)", with confidentiality "by encryption at an appropriate security strength (see SP 800-152) or by controlling access to the secret key information via physical means" [R6].
- **Every environment is the first custody phase today.** Keycloak 26.7.5 signs with a key pair it holds. Its documented key providers generate or load the pair inside the kernel [R11], and its vault serves passwords and secrets, not signing keys [R18]. So, in production too, the private key is in the kernel's memory while it is in use. SP 800-57 allows that: "Keys may be maintained within a cryptographic module while they are being actively used, or they may be stored externally (provided that proper protection is afforded) and recalled as needed" [R6]. NIST SC-12 leaves the key management requirements to the organization [R22]; this section is those requirements.
- **Non-exportable custody is a later phase.** A KMS or HSM that never releases the private key is adopted when an audit or regulatory obligation requires it. The pinned kernel's key providers hold the key pair themselves [R11], so that phase needs a kernel integration the pinned release does not document, and it is decided in its own ADR.
- **A throwaway kernel**, such as a test run's, may sign with a key it generated itself, because nothing outside that run verifies its tokens.

### 5.4 The Ingress Closes the Legacy Realm Endpoint (amended 2026-10-20)

**The pinned kernel generates an RS256 key when an anonymous request asks for its legacy realm endpoint.** Keycloak 26.7.5 serves `GET /realms/{realm}` to anyone and returns the realm's RS256 public key in it: `PublicRealmResource.getRealm` sets `rep.setPublicKeyPem(PemUtils.encodeKey(session.keys().getActiveRsaKey(realm).getPublicKey()))` [R23]. `getActiveRsaKey` asks for `getActiveKey(realm, KeyUse.SIG, Algorithm.RS256)` [R24]. The realm's RS256 provider is disabled, because the JWKS advertises `PS256` keys only (§5.1), so no RS256 key is active. `DefaultKeyManager.getActiveKey` then asks a key provider factory to create fallback keys, and logs "No keys found for realm={0} and algorithm={1} for use={2}. Generating keys." [R24]. That key is generated in the kernel, which §5.3 forbids ("No replica generates key material"), and it is published beside the `PS256` key, which §5.1 forbids.

- **Every ingress that serves the realm answers `404` to `GET /realms/{realm}`**, the realm's root path and nothing below it, matched without regard to case, with repeated or trailing slashes, matrix parameters or percent-encoding, on the decoded path. Caddy's `path_regexp` "Runs against the URI-decoded/unescaped path" [R26]. identity-kernel's development proxy closes `(?i)^/+realms/+[^/]+/*$` on every listener (identity-kernel #71, TDD-identity-kernel-002 §The Published Key Set).
- **No client loses anything.** Discovery, the key set and the token endpoint are below the realm's root, and stay served. Keycloak asks for only some paths to be exposed: "When using a reverse proxy, Keycloak only requires certain paths to be exposed", with `/realms/` exposed because "This path is needed to work correctly, for example, for OIDC endpoints" [R25]. Only the root of one realm is closed.
- **The kernel refuses what gets past the proxy.** `realm-apply` refuses any enabled key whose public key is not the keystore's, so a `fallback-RS256` made by a caller on the internal network fails the next run. identity-kernel's compatibility suite records what the pinned image does on that endpoint, so a Keycloak upgrade that changes it is seen.
- **It is a production gate** (`STD-GLB-009` §Security & Access Governance, 2.0.0, which this section authorizes). No production ingress exists yet. Its configuration closes the endpoint before the realm serves anyone, and a test against the public host proves the `404` for each spelling, as identity-kernel's `deploy-dev` proves it for the development server.

### 5.5 Rotation Decisions (amended 2026-10-24)

identity-kernel #75 proved the mechanism of each state on the pinned release: a `staged` or `retiring` key is an enabled, passive `java-keystore` provider; an activation makes the new key active before it demotes the old one, because with no active key the kernel generates a fallback key (§5.4); and a key leaves the key set when, and only when, its provider is removed. It left seven questions that the mechanism cannot answer. Each is decided below, with the options, the first-class sources, and the choice where the sources are silent.

Where a source is silent, the conservative option is the one that keeps fewer copies of private material, fewer privileged operations on the active key, and a record that cannot be edited afterwards.

**Q3. Custody of more than one key: one keystore and two secrets per key.**

- **Options.** (a) One keystore with an alias per key, in one secret. (b) One keystore per key, each with its own keystore secret and password secret.
- **Decision: (b).** Each keystore holds exactly one RSA-3072 pair under the alias `realm-signing`, so the image's start check keeps its alias and is applied to every keystore file it finds. A keystore with a second entry is refused. The file and the secret carry the `kid`, which is the key's RFC 7638 thumbprint (§5.2) and so never repeats [R7]. RFC 7517 uses the `kid` for exactly this: "This is used, for instance, to choose among a set of keys within a JWK Set during key rollover" [R27]. The exact vault-safe spelling of the name is the TDD's.
- **Why.** Adding or removing an entry in a shared keystore means writing a new version of the one secret that holds every key. The new version is written while the active key is in it, so each staging touches the active key's custody. Every older version still carries whatever key it carried, and Q8 shows that AWS gives no way to remove one version on demand. With a secret per key, staging a key never touches another key's secret, and the secret is deleted whole.
- **Keycloak side.** Each key is one provider, as the guide has it: "Start by creating new keys with a higher priority than the existing active keys" [R11].
- **Cost.** A key's two secrets are objects in the `SecretProviderClass` [R20], so staging a key is a manifest change and a rolling restart of the replicas before its provider is created, and retiring it is the reverse. A secret of one pair stays far under the size limit [R19].
- **Rejected.** (a): it ties retirement to rewriting the secret of every other key, and its old versions keep the retired key.

**Q4. Who owns the signing providers' state: the rotation steps, and `realm-apply` checks invariants.**

- **Options.** (a) The realm definition declares every provider, with its flags and priority from a per-environment source. (b) The rotation steps own the providers, and `realm-apply` checks only invariants.
- **Decision: (b).** A provider's presence, `active` flag, `enabled` flag and priority change only through a rotation step. `realm-apply` never changes or removes a signing provider that exists. It fails the run unless: exactly one enabled `PS256` key is active and carries the highest priority among the active keys; every enabled key's public key is the public key of a keystore in custody; no other key exists, so no `fallback-PS256` and no RS256 key; and the retirement floor holds. The first key is the one exception: when the realm has no signing provider, `realm-apply` creates one, active, from the one keystore in custody, and refuses when there is more than one. Without that, the realm would serve a request before its first activation and the kernel would generate a fallback key (§5.4).
- **Why.** Keycloak describes rotation as a sequence of operations on a running realm: "Once new keys are available, all new tokens and cookies will be signed with the new keys" [R11]. A definition that declares the flags is a second writer. Re-applying an older definition would demote the active key, and between that call and the next the kernel would generate a fallback key. A per-environment source that lists every provider is a second registry, edited by hand and approved nowhere. A state that needs an approval (Q9) cannot come from a file an apply reads. Separation of duties asks that the person who changes the realm's configuration is not the person who acts on key material: "Separation of duties addresses the potential for abuse of authorized privileges and helps to reduce the risk of malevolent activity without collusion" [R31].
- **Rejected.** (a), for the second writer and the second registry.

**Q5. Where the key registry lives: the Control Database, as insert-only rows.**

- **Options.** (a) The ceremony record in the keys directory, and an entry on the change ticket, as built. (b) A store of the registry's own in the secret manager's account. (c) The Control Database of the Identity Control Service, beside the bootstrap ceremony's evidence (`ADR-IAM-001` §5.11).
- **Decision: (c).** The registry is a table of transitions, each row insert-only: the `kid`, the transition, the actor, the approver (Q9), the reason, the correlation identifier and the time. `public_jwk`, the algorithm and `custody_ref` are written once, when the key is staged, and never changed. A key's state is its latest row. The keys directory keeps only the ceremony's file. The registry does not depend on it, and the keys directory stays unbacked up (§5.3).
- **Why.** NIST gives the duty and the reason: for the pre-activation state, "Information about the generation of the key shall be recorded", and for the destroyed state, "Although the key no longer exists, its previous existence may be recorded (e.g., in metadata or audit logs)" [R6]. Its reason for keeping the record: "records of the identifier of the key, its type, and its cryptoperiod may be helpful in determining what information was protected under the key and how best to recover from the compromise" [R6]. The record has to outlive the key, the realm and a redeployment of the key directory, so it cannot live where the key lives. A ticket is not insert-only and a machine cannot check it. The Control Database already holds an insert-only, single-purpose evidence row for the ceremony that creates the first Principal, and its rows are the estate's durable record. The registry is evidence and holds no authority over the key (TDD-identity-kernel-002 §Key Registry).
- **Rejected.** (a): the file is lost with the directory and the ticket cannot be queried. (b): it is a new store with a new backup and retention to own, for a record the Control Database already keeps.
- **Follows.** identity-control's TDD says how the Control Database's backup and retention keep these rows for as long as `STD-IAM-001` §3.8's audit record is kept.

**Q6. Rollback: a staged key may be abandoned, and a retiring key is never reactivated.**

- **Options.** For a staged key that never signed: (a) abandon it as `retired`, (b) as `revoked`, (c) as a new state. For a retiring key: (d) it may be activated again within its window, (e) it may not.
- **Decision: (a) and (e).** Abandoning is the staged key's transition to `retired`, with the reason `abandoned` in the registry row. NIST names it: "If a key is in the pre-activation state, and it has been determined that the key will not be needed in the future, the key shall transition directly from the pre-activation state to the destroyed state" [R6]. `retired` is the destroyed state in §5.2's table, so no state is added. It is `revoked` only when the key's integrity or confidentiality is suspect, which NIST handles the same way as any suspected compromise: "then the key shall transition from the pre-activation state to the compromised state" [R6]. Abandoning removes the provider and destroys the private material (Q8) under an approval (Q9). The public key stays in the registry.
- **A retiring key is not activated again.** NIST's transitions out of the deactivated state go to two places, and neither is the active state: "A key shall transition from the deactivated state to the compromised state when the integrity of a key or the confidentiality of a key requiring confidentiality protection becomes suspect", and "When no longer needed (e.g., to decrypt data), symmetric (secret) and asymmetric private keys in the deactivated state shall transition to the destroyed state" [R6]. NIST restores a key to the active state only from its suspended state, which this lifecycle does not have, and adding one is not needed. When a new key fails, the recovery is to fix or replace the new key: a new key is staged, and Q7's timing applies if the failure is a compromise. The old key, still retiring, continues to verify.
- **Rejected.** (b) and (c), for an abandoned key that was never suspect. (d), because it makes a demoted key's private material a standing fallback and gives two keys a claim to be the active one.
- **Mechanically possible, so stated.** Keycloak can toggle a provider's `active` flag back [R11]. The platform declines to, so that the registry's transitions stay the ones NIST defines.

**Q7. Activation after a compromise: activate at once.**

- **Options.** (a) Wait the 10-minute consumer cache window, as a scheduled activation does, while the compromised key keeps signing. (b) Activate at once and rely on consumers refetching on an unknown `kid`.
- **Decision: (b).** A replacement key that was already `staged` for at least the window is activated. When there is none, a replacement is generated, staged and activated without waiting. The compromised key is then moved to `revoked`: its provider is removed and its private material destroyed (Q8). The new key is active before the old one is removed, so no moment has no active key (§5.4).
- **Why.** Keycloak's own instruction: "if you think that your realm signing key was compromised, you should first generate new key pair as described above and then immediately remove the compromised key pair. Alternatively, you can delete the provider from the Providers table" [R11]. NIST asks for speed over a quiet transition: "a cryptographic key should be revoked as soon as feasible after the need for revocation has been determined" [R6]. The consumer's side is OpenID Connect Core's: "The verifier knows to go back to the jwks_uri location to re-retrieve the keys when it sees an unfamiliar kid value" [R5]. Waiting leaves the signing key in the attacker's hands for the whole window, which buys consumers nothing they need, because a refetch is the specified way to meet a new `kid`.
- **Cost, stated.** A consumer whose key set cache predates the activation rejects tokens that carry the new `kid` until its rate-limited refetch succeeds, and a consumer whose cache still holds the revoked key accepts its tokens for at most the cache lifetime of 10 minutes. §5.2's "fails verification from that moment" is amended to say so. NIST says the same of a compromise generally: "an immediate damage assessment should be conducted" [R6], and the registry holds the issuance window it needs (Q5).
- **Not adopted.** Keycloak's not-before push reaches only clients that have an Admin URL set [R11]. Platform consumers verify from the key set, so the key set is the channel, and the push stays an optional step in a runbook for a client that has one.
- **Approval is not waived.** An approver other than the operator is still recorded before the step (Q9), and it is any one holder of the ceremony role (`STD-IAM-001` §3.10). Only the waiting is dropped.

**Q8. Destroying every stored secret version in production: delete the key's secrets whole, and never write a second version.**

- **Options.** (a) One secret for all keys: delete it without recovery and create it again with the remaining keys. (b) Remove the labels from the versions that carry the retired key and wait for Secrets Manager to prune them. (c) Delete the secret with a recovery window. (d) One secret pair per key (Q3), each written once, deleted with no recovery window.
- **Decision: (d).** No step calls `PutSecretValue` or `UpdateSecret` on a signing secret, and the key's policy denies both, so each secret has one version for its whole life. Retiring, revoking or abandoning a key then runs these steps in order, after the approval (Q9) and after the registry confirms the key's state allows it:
  1. Remove the key's provider, which takes it out of the key set.
  2. Remove its two objects from the `SecretProviderClass` and roll the replicas, so no manifest names a secret about to go.
  3. Delete its keystore secret and its password secret with `ForceDeleteWithoutRecovery`.
  4. Read each secret until Secrets Manager no longer returns it, and take the `DeleteSecret` event of each from CloudTrail.
  5. Record `retired_at` or `revoked_at` in the registry with those events, and not before.
- **Why.** AWS gives no way to remove one version: "You can't directly delete a version of a secret. Instead, you remove all staging labels from the version using the AWS CLI or AWS SDK." Even then, removal waits for Secrets Manager: "Secrets Manager never removes labeled versions, but unlabeled versions are considered deprecated. Secrets Manager removes deprecated versions when there are more than 100. Secrets Manager doesn't remove versions created less than 24 hours ago" [R28][R29]. Destruction that waits for a hundred more versions is not destruction a step can prove. Deleting the secret removes every version it holds, and AWS says what the force option costs: "If you delete a secret with the ForceDeleteWithoutRecovery parameter, then you have no opportunity to recover the secret. You lose the secret permanently." [R30]. Here that is the aim: a recovery window would keep the private key recoverable, and "a copy kept in cold storage is a copy that can still sign" (§5.2). The default is not that: "a recovery window of a minimum of seven days" [R29]. NIST's meaning of destruction is "To remove all traces of a cryptographic key so that it cannot be recovered by either physical or electronic means" [R6]. AWS deletes asynchronously: "there might be a short delay before the secret is permanently deleted" [R30], which is why step 4 reads until it is gone.
- **No replicas.** A signing secret is not replicated to another Region, because "You can't delete a primary secret if it is replicated to other Regions" [R29] and a replica is one more copy to destroy. If a replica is ever approved, deleting it comes first, and it is its own decision.
- **The KMS key stays.** One customer-managed KMS key serves every key of an environment and realm (§5.3). Retiring a signing key does not touch it.
- **Rejected.** (a): it puts the remaining keys, the active one included, through a delete and a re-create in a window with a new ARN and a new policy, and its old versions still hold the retired key until the delete. (b), for the reasons above. (c), for the copy it keeps.
- **Development server.** The two files of the key are removed from `deploy/dev/keys/`. The server is redeployed from zero and never backs a key up (§5.3).

**Q9. Approvals and the event: the registry records the approval, and its row is the event.**

- **Options.** For the approval: (a) the change ticket, as the ceremony keeps its review, (b) an insert-only row in the registry (Q5). For the event of a step outside Keycloak: (c) the kernel's native admin event store alone, (d) CloudTrail alone, (e) the registry's row, corroborated by the two native sources.
- **Decision: (b) and (e).** An activation needs an approval row by a holder of the ceremony role who is neither the operator who generated the key nor the operator of the step. A retirement, abandonment or revocation needs one by a holder who is not its operator. The registry refuses the row when the approver equals the operator, as the ceremony's record refuses a reviewer who ran it (`STD-IAM-001` §3.10), and the step refuses to run without an approval row for that `kid` and that transition. The approval is for one transition of one `kid`, so it cannot be reused.
- **The event.** Each transition row the registry takes carries actor, approver, reason, correlation identifier and outcome. The Identity Runtime keeps it as a privileged-administration event in its durable record until Audit & Evidence has it (`STD-IAM-001` §3.8). Two native sources corroborate it by the correlation identifier. A provider change through the admin API appears in the kernel's admin events, with the representation on: "The Include Representation switch includes JSON documents sent through the admin REST API so you can view the administrators actions" [R11]. A secret's creation or deletion appears in CloudTrail: "AWS CloudTrail records all API calls for Secrets Manager as events" [R21], and "Secrets Manager generates a CloudTrail log entry when you delete a secret" [R29].
- **Why.** NIST AC-5: "Separation of duties addresses the potential for abuse of authorized privileges and helps to reduce the risk of malevolent activity without collusion" [R31]. NIST AU-2 asks to "Specify the following event types for logging within the system" and names "administrative privilege usage" among the types; AU-12 asks to "Generate audit records for the event types defined in AU-2c that include the audit record content defined in AU-3" [R31]. A step that runs outside Keycloak, a secret deleted or a file removed, leaves no kernel event, and CloudTrail records the call but not the approval or the reason. The registry row holds all of it in one record.
- **Rejected.** (a): a ticket is editable and a step cannot check it. (c) and (d) alone: each sees part of a step.
- **Mechanism.** The step is a command on the Identity Control deployable, as the bootstrap ceremony is (`ADR-IAM-001` §5.11), so no new endpoint exists to protect. identity-control's TDD says how it takes the approval and the kernel's steps call it.

## 6. Consequences

### Positive

- One algorithm, one key lifecycle, and no algorithm branch in any verifier.
- A rotation fails no valid token, and a compromise ends trust in a key at once.
- No private signing key outlives its use, and none exists outside approved custody.

### Negative

- A relying party that can verify only `RS256` needs an exception record, with an owner and an expiry.
- The platform declares a departure from RFC 9068 §2.1 and OpenID Connect Core §15.1, which a conformance test would report.
- Tokens are about 426 bytes larger than `ES256` tokens.
- A key ceremony is an operation two people must be available for.
- Every environment keeps the private key in the kernel's memory while it signs. Non-exportable custody waits for its own decision (§5.3).
- A lost development keystore cannot be restored. It costs a new ceremony and a new `kid`, and every development token signed before it fails.
- A key's destruction is irrecoverable by design (§5.5 Q8). A wrong delete of a signing secret costs a new key, so the steps guard it by the registry's state and an approval.
- Staging and retiring a key change the manifest and roll the replicas (§5.5 Q3), and a compromise response does too.
- Activation after a compromise lets a consumer with a stale cache reject the new key's tokens for a short time, and accept the revoked key's for at most the cache lifetime (§5.5 Q7).
- The registry and the approvals sit in identity-control, so a rotation step needs the Identity Control deployable (§5.5 Q5, Q9).

### Operational

- The rotation schedule publishes the next key before activating it, and the retirement window is recomputed from the live token lifetime classes rather than read as a constant.
- Rotation steps own the signing providers, and `realm-apply` checks invariants only (§5.5 Q4).
- A key's retirement deletes its two secrets with no recovery window, and takes the `DeleteSecret` events from CloudTrail into the registry (§5.5 Q8).
- Activation, retirement, abandonment and revocation each have a recorded approval by someone other than the operator (§5.5 Q9).
- The identity kernel's compatibility suite proves `PS256` issuance and verification on every candidate release; a candidate that cannot issue `PS256` is not promoted.
- The secret manager holds the only copy of an active or retiring private key; destroying it at retirement is part of the rotation, and is recorded.
- Every ingress in front of the realm answers `404` to `GET /realms/{realm}`, and production does not go live until a test proves it (§5.4).
- Production manifests name the secret in a `SecretProviderClass`, and the realm declares the `java-keystore` provider with `${vault.…}` passwords. The kernel is built with the file vault enabled.

## 8. Alternatives Considered

### Alternative A: `ES256` Only

- **Pros**: the most compact tokens, and an algorithm FAPI 2.0 permits [R9].
- **Cons**: ECDSA verification is the slower operation on the path that repeats [R13]. An `ES256` signature is the raw concatenation of R and S [R1], while signing services such as Vault Transit produce ASN.1 DER by default [R14], so every signer needs a conversion that is a known source of defects.
- **Why Rejected**: it saves header bytes and pays for them on every verification.

### Alternative B: Ephemeral Keys in Production

- **Pros**: no custody to operate.
- **Cons**: a key generated by one replica is unknown to the others, so tokens it signs fail verification elsewhere, and every restart replaces the key and fails every token signed before it.
- **Why Rejected**: it breaks verification continuity, which `STD-IAM-001 §3.5` exists to guarantee.

### Alternative C: `ES256` Internally and `RS256` Externally

- **Pros**: the compact-token argument for internal traffic, and `RS256` acceptance by every relying party without an exception record.
- **Cons**: two algorithms require two key lifecycles and an algorithm branch in every verifier, which is where algorithm confusion lives [R3]. The external half selects PKCS#1 v1.5, which carries no security proof [R2] and which FAPI rejects [R9][R10].
- **Why Rejected**: it pays in key custody and verifier surface for a saving too small to matter.

### Alternative D: `Ed25519` as the Baseline

- **Pros**: compact, fast, and deterministic, so free of the nonce-reuse failure that makes ECDSA implementations fragile [R8]; FAPI 2.0 permits it [R9].
- **Cons**: in this platform's assessment, relying-party and gateway support across the OpenID Connect ecosystem is thinner than for RSA, and an external party that cannot verify it has no fallback inside a single-algorithm profile.
- **Why Rejected**: the stronger choice cryptographically and the riskier one for a profile that must also serve external federation. Revisit when relying-party support is no longer the limit.

### Alternative E: Support `RS256` Beside `PS256`, to Conform to RFC 9068

- **Pros**: conformance with the mandatory-to-implement rules of RFC 9068 and OpenID Connect Core [R4][R5], and no exception records.
- **Cons**: it is Alternative C's second key lifecycle and verifier branch again, for an algorithm without a security proof.
- **Why Rejected**: the exception serves the relying parties that need `RS256`, and nothing else in the estate does.

### Alternative F: A Non-Exportable KMS or HSM Key That Signs Tokens Now

- **Pros**: the private key never leaves the hardware boundary [R15].
- **Cons**: the pinned kernel cannot use one. Its key providers, `rsa-generated`, `rsa` and `java-keystore`, hold the key pair themselves [R11], so it needs a custom key-provider SPI that the pinned release does not document.
- **Why Rejected**: not for now. It is the second custody phase of §5.3, decided in its own ADR when an audit or regulatory obligation requires it.

### Alternative G: HashiCorp Vault, KV for the Keystore or Transit to Sign

- **Pros**: one secret store across clouds; Transit keeps the key inside Vault.
- **Cons**: Transit has Alternative F's blocker, because the kernel signs locally. KV works, but it adds a self-run secret-management cluster where the adopted cloud already offers a managed one, and `EAD-005` asks for managed custody.
- **Why Rejected**: it is more to run and gains nothing the managed service lacks.

### Alternative H: A Plain Kubernetes Secret as the Custody Store

- **Pros**: no cloud dependency, and the kernel's file vault reads it directly [R18].
- **Cons**: it is not the managed KMS or HSM capability `EAD-005` names, and its reads are not recorded the way CloudTrail records a secret's [R21].
- **Why Rejected**: a Kubernetes Secret may carry the keystore into the pod, but it is never the custody.
